## Decisions settled before drafting

**The two truncated-prior inverse Stan models are archived.** Spec section 9.8
left this open. `docs/why_plugin_p50_differs.md` was the only justification for
keeping `invT_gen_logi_fixed_{univ,multiv}_marginal_truncated_prior.stan` in the
wheel, and that page is deleted because the plug-in-versus-Bayesian P50 argument
appears nowhere in the revised manuscript. So both models move to
`archive/pre-submission/stan_models/`, and `constraint_type` and `min_temp`
leave the public API, narrowing `predict_T_from_proxyObs` to the unconstrained
inverse the paper actually uses.

Consequence: **the wheel ships 7 Stan models, not 9.** Spec verification item 3
changes accordingly. Plan 01 sets `.zenodo.json` to 9 (true at that point) and
plan 04 lowers it to 7.

`utils/naming.py::CONSTRAINT_CODES` is **not** narrowed. It is a name grammar
that must keep decoding case ids of reconstructions already on disk and on
Zenodo; narrowing it would orphan those files.

Three plans edit notebooks under `notebooks/manuscripts/`, and `nbformat` writes
the whole file. **Only one notebook-editing plan may be in flight at a time**,
and every notebook task must re-read the file immediately before editing.

| notebook | plan 02 | plan 03 |
|---|---|---|
| `SI_code02_t0shift_TEXAS_analysis.ipynb` | cell 89 (`temp_param`, `y_param`) | import cells |

In every case the edit is to **cell source only**. Executed outputs are left
untouched: they record what ran, and rewriting them would falsify that record.

So today: the tests run, but the notebooks cannot be executed, linted or edited,
and the docs cannot be built.

What each plan needs that is currently missing:

| plan | needs | for |
|---|---|---|
| 02, 03 | `nbformat` | editing notebook cell source |
| 03 | `nbconvert`, `ruff`, `pyflakes`, a working kernel | the (a)(b)(c) import checks |
| 02, 03 | `ultraplot`, `cartopy`, `pykrige`, `scikit-learn`, `arviz` | executing SI_code02 and SI_code00 |

| 05 | `jupyter-book<2` | building the docs |
| 03 | `conda-lock`, `docker` | regenerating the locks and the image |

**Build it under a fresh name.**

```bash
conda env create -f environment.yml -n texas-env-2026-09
conda run -n texas-env-2026-09 pip install -e ".[all]"
conda run -n texas-env-2026-09 python -m pytest -q     # expect 351 passed, 11 skipped
```

**`environment.yml` itself is fine — it solves cleanly.** A build that fails
with a matplotlib / matplotlib-base conflict mentioning python 3.7 and pypy3.7
is the **name collision** with the stale `texas-env`, not a bad spec. Verified
with `conda env create -f environment.yml -n <fresh> --dry-run`, which returns a
506-line solution including `esmpy`, `xesmf` and `pygplates`.

Do this **before** plan 03 edits `environment.yml`, so the environment measured
is the pre-change baseline the audit is written against.

**Open question for the user:** whether to replace the stale `texas-env` in
place. Deleting a conda environment is destructive, so it is not done
autonomously. Until it is decided, use the fresh name above, and note that
`docker/Dockerfile` creates its own `texas-env` *inside the image* from
`conda-lock.yml` — that one is unrelated to the local stale environment and is
not affected either way.

The `uv` route cannot fully substitute: `xesmf` needs `esmpy`, which is not on
PyPI, so the `regrid` extra is conda-only. `uv` remains fine for adding a single
pure-Python tool to `.venv` (`VIRTUAL_ENV=.venv uv pip install <pkg>`), which is
how `pytest` got there.

## Corrections to the spec found while planning

1. **Item 7's arithmetic.** The spec expects 55 LFS files after untracking,
   reasoning "22 spreadsheets + 32 revision1 + 1 figure". Three of the 22 kept
   spreadsheets are not LFS-tracked: `.txt` and `.parquet` match no filter in
   `.gitattributes`. The real target is **52**. Verified against the live index.
2. **The `fitted_models/` negation.** The spec's draft `.gitignore` re-includes
   `data/spreadsheets/fitted_models/` and then excludes its contents, with no
   negation inside. The only file there is the duplicate `.pkl` that Appendix A
   untracks, so the pair tracks nothing. Dropped in plan 01.
3. **`.zenodo.json` says the package "ships 20 Stan models"** with ensemble
   sampling and hard temperature constraints. All three claims are wrong: both
   families were archived in April 2026. Corrected in plan 01, then again in 04.
4. **Section 5b counts 13 `kriged_halo_*.npz` files.** There are **15**, so the
   per-machine migration frees about 189 MB rather than 185. Verified by
   `ls data/cache/kriged_halo_*.npz | wc -l`. Corrected in plan 02.
5. **Section 5b item 7 says `docs/troubleshooting.md` names the cache** where it
   describes it. That page has no cache section at all, so plan 02 appends one
   rather than amending a passage that does not exist.
6. **`.dockerignore` ignores `stan_models_explanation_v2.pdf`**, a PDF export of
   a docs page. No such file has ever existed here. Dropped in plan 01 alongside
   the phylogenomics block.

7. **Section 9.4 says SI_code00, 02 and 03 contain `from TEXAS import *`.** The
   actual line in all three is **`from TEXAS.plotting import *`**, a much
   narrower import. Verified by grep. This changes the fix: SI_code02 becomes an
   explicit `import plot_prior_distributions, plot_residual_maps`, while
   SI_code00 and SI_code03 use none of that module's eleven exports, so the line
   is deleted outright rather than replaced. Corrected in plan 03.
8. **Several section 9.4 entries are not in import cells at all.** Plan 03 names
   the exact cell indices instead of assuming one import cell per notebook.

## One bug found in the plans themselves

Worth recording, because it is the kind of error that survives review by looking
reasonable.

Plan 01's first draft repointed `utils/paths.py::STAN_ARCHIVE_DIR` at the new
`archive/pre-submission/stan_models/` directory, on the assumption that the
constant tracked the directory being moved. **It does not.** It has always
pointed at `archive/submission-2026-04/stan_models`, which is a different
directory that this work does not touch. Repointing it would have broken
plain-stem resolution for the eight 2026-04 models that
`tests/test_stan_model_archive.py` asserts on and that `SI_code02a` loads.

Plan 01 now leaves `paths.py` and the compiler fallback alone, and its
verification asserts the 2026-04 fallback still resolves rather than asserting
something false about the new directory. Caught by the plan 04 author reading
the constant instead of the plan.

**Consequence for the pre-submission archive:** nothing in it resolves by plain
stem, before or after the move. That is unchanged behaviour, not a regression.
Everything there is reachable by absolute path, which `archive/README.md`
documents.
